# AI 网关服务 — 需求清单与开发计划

> 文档版本：v0.1  
> 日期：2026-11-02  
> 技术栈：NestJS + MySQL 8.0 + Redis / Vue 3 + Element Plus + Element Plus X  
> 文档目的：在开始编码前锁定 MVP 范围、关键规则、数据模型、接口与排期，避免后期反复。

---

## 0. 结论先行

建议第一版做一个 **OpenAI 兼容的 AI 网关 MVP**，优先打通一条完整链路：

```
管理端登录 → 配置上游 → 配置模型路由 → 签发 Key → 客户端调用 → 流式返回
→ 敏感内容拦截 → 限流/配额 → 调用日志 → 仪表盘
```

第一版建议支持：

- **上游协议**：OpenAI-Compatible、Anthropic Messages、Google Gemini；Azure OpenAI 放到 P1。
- **对外协议**：`POST /v1/chat/completions`（流式/非流式）+ `GET /v1/models`，与 OpenAI SDK 兼容。
- **管理端**：上游管理、模型路由、Key 管理、敏感规则、调用日志、仪表盘、在线调试。
- **基础设施**：MySQL 8.0 + Redis 7 + Docker Compose。
- **部署形态**：单管理员、单租户、可水平扩展；多租户/计费充值不做进 MVP。

> 这样第一版能覆盖你提出的 7 项核心诉求，同时把“多协议、多上游、Key 分发、模型白名单、日志、敏感拦截、IP/频次限制”形成闭环。

## 1. 产品定位与范围

### 1.1 产品定位

面向团队内部或客户的 **统一大模型接入层**：

- 上游：统一管理多家模型厂商、多个账号、多种协议。
- 下游：用一套 OpenAI 兼容 API 接入业务，降低切换成本。
- 管控：按 Key 分配模型权限、IP 权限、调用频次和配额。
- 安全：对用户输入和模型输出做敏感信息检测、拦截、脱敏和留痕。
- 可观测：每次调用可追溯，能看耗时、Token、错误、拦截原因。

### 1.2 角色

| 角色 | 说明 | MVP |
|---|---|---|
| 管理员 Admin | 配置上游、模型、Key、规则，查看日志和统计 | ✅ |
| 调用方 API Consumer | 使用网关签发的 Key 调用 `/v1/*` | ✅ |
| 审计员 Viewer | 只读查看日志、统计、配置 | P1 |
| 租户管理员 | 多租户隔离 | P2 |

### 1.3 MVP 不做

- 不做模型托管、微调、训练。
- 不做充值、支付、账单、发票。
- 不做知识库/RAG/提示词工程平台。
- 不做复杂多租户和细粒度 RBAC（表结构预留角色字段）。
- 不做语义级内容审核（第一版用关键词 + 正则 + 内置 PII/密钥规则；外部审核 API 放 P2）。
- 不做移动端 App；管理端做响应式 Web。
- 不做多地域容灾；先支持单地域多实例。

### 1.4 优先级定义

| 优先级 | 含义 |
|---|---|
| P0 | MVP 必须，缺失则无法验收 |
| P1 | 第一版后尽快补，影响体验或生产强度 |
| P2 | 后续演进，不进入首版排期 |

### 2.4 部署拓扑

```
Internet / 内网
      │
```

- API 无状态，可水平扩展；限流与并发计数集中在 Redis。

- Nginx 对 SSE 必须关闭缓冲：`proxy_buffering off; proxy_cache off;`，并放宽读超时。

## 3. 功能需求清单

### 3.1 上游接入（UP）

| 编号 | 需求 | 说明与规则 | 优先级 |
|---|---|---|---|
| UP-01 | 多协议适配 | 支持 OpenAI-Compatible、Anthropic Messages、Gemini generateContent；统一转换为内部 `ChatRequest / ChatResponse / StreamEvent` | P0 |
| UP-02 | 多上游管理 | 可创建多个来源，字段含名称、类型、Base URL、凭证、超时、重试、优先级、权重、启用状态 | P0 |
| UP-03 | 凭证安全 | 上游 API Key 使用 AES-256-GCM 加密存储，接口只返回掩码；日志、错误信息不得出现明文 | P0 |
| UP-04 | 连通性测试 | 管理端一键测试；支持调用 `/models` 或最小化 chat 请求；返回耗时和错误原因 | P0 |
| UP-05 | 模型发现/登记 | 支持从上游拉取模型列表，也支持手工登记上游模型名 | P1 |
| UP-06 | 路由与故障转移 | 公共模型可绑定多个上游模型；按优先级 + 权重选择；特定错误自动切换下一个 | P0 |
| UP-07 | 熔断与冷却 | 连续失败达到阈值后短暂熔断，半开探测恢复 | P1 |
| UP-08 | 健康检查 | 定时探测上游状态，在管理端展示健康/降级/不可用 | P1 |
| UP-09 | 能力透传 | 支持 tools/function calling、JSON mode、vision、reasoning 内容；不支持的能力明确报错 | P0/P1 |
| UP-10 | 自定义 Header / 代理 | 适配企业网关、代理、特殊鉴权 | P2 |
| UP-11 | 上游并发限制 | 按上游/模型限制并发，避免打爆账号配额 | P1 |

**路由规则：**

1. 公共模型 `model` 查到多条 `route`，按 `priority` 升序分组。
2. 同优先级内按权重随机；过滤禁用、熔断、能力不匹配的上游。
3. 首选失败且满足重试条件时，切到同优先级下一个；再切下一优先级。
4. 所有候选失败 → `503 no_available_upstream`，日志记录每次 attempt。
5. 流式请求只在“尚未向客户端发送首字节”前重试；已开始输出后不重试。

**可重试错误：** 连接失败、DNS/TLS 错误、响应头超时、408、429、500、502、503、504。  
**不重试：** 400、401、403、404、422（通常是请求本身或凭证问题，重试无意义）。

### 3.2 对外 API（API）

| 编号 | 需求 | 说明与规则 | 优先级 |
|---|---|---|---|
| API-01 | OpenAI 兼容对话 | `POST /v1/chat/completions`，支持 `stream=true/false` | P0 |
| API-02 | 模型列表 | `GET /v1/models`，只返回该 Key 有权限且启用的模型 | P0 |
| API-03 | 统一错误格式 | 使用 OpenAI 风格 `{"error":{...}}`，附 `request_id` | P0 |
| API-04 | 流式用量 | 支持 `stream_options.include_usage`，最后一个 chunk 返回 usage | P0 |
| API-05 | 请求 ID | 响应头 `x-gateway-request-id`；客户端可传 `x-request-id`（做长度/字符校验） | P0 |
| API-06 | 断连取消 | 客户端断开时 Abort 上游请求，释放并发槽位，日志记为 `cancelled` | P0 |
| API-07 | 请求限制 | Body 大小、消息条数、单条字符数、总字符数、超时均可配置 | P0 |
| API-08 | 限流响应头 | `x-ratelimit-*`、`retry-after`，便于客户端自适应 | P0 |
| API-09 | Anthropic 兼容入口 | `POST /v1/messages`，把 Anthropic 请求转为内部格式 | P1 |
| API-10 | Embeddings | `POST /v1/embeddings` | P2 |
| API-11 | Responses API | `POST /v1/responses` | P2 |
| API-12 | Gemini 原生入口 | `POST /v1beta/models/{model}:generateContent` | P2 |

**请求示例：**

```bash
curl http://localhost:3000/v1/chat/completions \
  -H "Authorization: Bearer sk-gw-xxxxxxxx" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "你好"}],
    "stream": true
  }'
```

**SSE 输出保持 OpenAI 格式：**

```
data: {"id":"chatcmpl-...","object":"chat.completion.chunk","choices":[{"delta":{"content":"你"}}]}

data: {"id":"chatcmpl-...","object":"chat.completion.chunk","choices":[{"delta":{},"finish_reason":"stop"}],"usage":{...}}

data: [DONE]
```

### 3.3 模型管理（MOD）

| 编号 | 需求 | 说明与规则 | 优先级 |
|---|---|---|---|
| MOD-01 | 公共模型登记 | 对外暴露的模型名，如 `gpt-4o-mini`、`claude-sonnet`、`deepseek-chat` | P0 |
| MOD-02 | 多上游映射 | 一个公共模型绑定多个“上游 + 上游模型名”，支持优先级/权重 | P0 |
| MOD-03 | 能力标签 | chat、vision、tools、json、reasoning、embedding；用于校验和前端展示 | P0 |
| MOD-04 | 上下文与价格 | 上下文窗口、输入/输出单价（每 1M tokens），用于展示和成本估算 | P1 |
| MOD-05 | 模型别名 | 支持把旧模型名指向新模型，便于平滑迁移 | P1 |
| MOD-06 | 启停与可见性 | 模型可全局停用；停用后 `/v1/models` 不返回，调用报错 | P0 |

### 3.4 Key 分发与权限（KEY）

| 编号 | 需求 | 说明与规则 | 优先级 |
|---|---|---|---|
| KEY-01 | 签发 Key | 生成 `sk-gw-` 前缀的高熵密钥；只在创建/轮换时展示一次 | P0 |
| KEY-02 | 安全存储 | 数据库只存 SHA-256 哈希 + 前缀 + 末 4 位；不存明文 | P0 |
| KEY-03 | 生命周期 | 启用、禁用、过期、轮换、吊销；吊销立即生效 | P0 |
| KEY-04 | 模型白名单 | 每个 Key 可勾选允许的模型；为空表示“不允许任何模型”或“全部”，需在设置中明确 | P0 |
| KEY-05 | IP 白名单 | 支持精确 IP、IPv4/IPv6 CIDR；为空表示不限制 | P0 |
| KEY-06 | 频次限制 | RPM（每分钟请求数）、并发数、每日请求数；可选 TPM（每分钟 Token） | P0 |
| KEY-07 | 配额 | 总请求数、总 Token、总成本、月度 Token/成本；超限拒绝 | P0 |
| KEY-08 | 元数据 | 名称、负责人、备注、过期时间、创建人 | P0 |
| KEY-09 | 用量概览 | 管理端查看 Key 的今日/本月请求、Token、拦截、错误率 | P1 |
| KEY-10 | 管理端测试 | 管理员可直接用某个 Key 发起测试调用，走完整策略链 | P1 |
| KEY-11 | 批量签发/导出 | 批量生成、CSV 导出（不含明文密钥） | P2 |

**Key 格式建议：**

```
sk-gw-<43 位 base64url 随机串>
```

- 随机源：`crypto.randomBytes(32)`。
- 查询：对完整 Key 做 SHA-256，按 `key_hash` 唯一索引查询。
- 展示：`sk-gw-abcd…wxyz`（前缀 + 末 4 位）。
- 不使用 bcrypt：Key 本身有 256 位熵，SHA-256 足够，且网关热路径需要低延迟。

**模型白名单语义（建议）：**

- 创建 Key 时默认“不授权任何模型”，必须显式勾选；避免误签发全权限 Key。
- 管理端提供“全选当前模型”快捷操作。
- 后续新增模型不会自动授权给已有 Key，需要管理员手动追加（更安全）。

### 3.5 敏感信息拦截（SEC）

| 编号 | 需求 | 说明与规则 | 优先级 |
|---|---|---|---|
| SEC-01 | 规则类型 | 关键词、正则、内置规则（身份证/手机号/银行卡/邮箱/API Key/私钥/JWT 等） | P0 |
| SEC-02 | 检测方向 | 输入、输出、双向 | P0 |
| SEC-03 | 处置动作 | `block` 阻断、`mask` 脱敏、`log` 仅记录放行 | P0 |
| SEC-04 | 策略集 | 默认策略 + 可创建多套策略；Key 可绑定策略，未绑定用默认 | P0 |
| SEC-05 | 内置 PII/密钥规则 | 身份证、手机号、银行卡（Luhn 校验）、邮箱、IPv4、JWT、AWS/GitHub/OpenAI/Anthropic 密钥、私钥头 | P0 |
| SEC-06 | 规避处理 | NFKC 归一化、去零宽字符、大小写归一；可选忽略空格/标点 | P0/P1 |
| SEC-07 | 流式输出拦截 | 滑动窗口检测跨 chunk 命中；命中后立即停止上游、发送安全收尾 | P0 |
| SEC-08 | 规则测试器 | 管理端输入样例，选择方向，实时高亮命中与最终动作 | P0 |
| SEC-09 | 拦截留痕 | 日志记录方向、规则、类别、动作、命中次数、脱敏片段；不记录完整敏感值 | P0 |
| SEC-10 | 误报白名单 | 按规则/文本片段加白 | P1 |
| SEC-11 | 命中统计 | 按规则/Key/模型统计命中趋势 | P1 |
| SEC-12 | 外部审核 | 接入 OpenAI Moderation、阿里云内容安全等 | P2 |

**流式输出处置建议：**

- `block` / `log`：P0 完整支持。
- `mask`：P0 先支持非流式；流式脱敏需要 holdback 缓冲（保留最大规则长度 + 安全边界），放 P1。流式下若规则配置为 `mask`，MVP 可按 `block` 处理并在文档中说明。

**检测顺序：**

```
输入：认证 → Key 状态 → IP → 模型白名单 → 限流 → 配额 → 输入检测 → 路由 → 上游
输出：上游响应 → 输出检测 → 转发客户端 → 用量/日志
```

先做限流再扫描，避免超大请求消耗检测 CPU；输入命中 `block` 时不调用上游，不计上游用量。

**命中后的返回：**

- 输入命中：
  - HTTP `400`
  - `code = content_policy_violation`
  - 返回通用提示 + `request_id`，不回显命中的敏感词。
- 输出命中（非流式）：
  - 返回 `200`，`finish_reason = content_filter`
  - `content` 替换为安全提示
  - 日志 `intercepted = true`
- 输出命中（流式）：
  - 停止读取上游
  - 发送安全提示 delta（可选）
  - 发送 `finish_reason = content_filter` 的 chunk
  - 发送 `[DONE]`
  - 日志记录命中规则和已输出内容长度

> 选择 `finish_reason=content_filter` 而不是 HTTP 错误，是为了兼容 OpenAI SDK 客户端的既有处理逻辑；同时通过日志和响应头 `x-gateway-intercepted: output` 明确标识。

## 4. 关键业务规则

### 4.1 调用链与拒绝顺序

```
1. 生成/接收 request_id
2. 解析 Authorization: Bearer sk-gw-...
3. 校验 Key 哈希、状态、过期时间
4. 校验客户端 IP 是否在白名单
5. 校验模型是否存在、是否启用、是否在 Key 白名单
6. 校验 RPM / 并发 / 每日请求
7. 校验总配额 / 月度配额
8. 扫描输入敏感信息
9. 选择上游路由
10. 调用上游（流式/非流式）
11. 扫描输出敏感信息
12. 统计用量、写日志
13. 返回响应
```

顺序原则：

- 认证和授权尽量靠前，避免无效请求消耗资源。
- 限流放在敏感扫描前，防止超大请求打满检测 CPU。
- 输入拦截命中时不调用上游，不产生上游费用。
- 日志最后写，失败不影响主响应；写日志异常降级到 pino。

### 4.2 Key 与认证

- 管理端：JWT Access Token（15 分钟，内存保存）+ Refresh Token（7 天，HttpOnly/Secure/SameSite=Lax Cookie，旋转刷新）。
- API 调用方：`Authorization: Bearer sk-gw-...`。
- Key 查找：SHA-256 → 唯一索引；命中后校验 `status`、`expires_at`。
- Key 禁用/吊销后立即失效（不缓存或短缓存 + 主动失效）。
- 管理端登录：argon2id 密码哈希；连续失败锁定（如 5 次/15 分钟）。

### 4.3 IP 白名单

- 支持 `1.2.3.4`、`10.0.0.0/8`、IPv6 CIDR。
- IPv4-mapped IPv6 统一归一化。
- 为空 = 不限制。
- 只有在配置了可信代理时才读取 `X-Forwarded-For` / `X-Real-IP`；否则使用 socket 地址，防止伪造。
- Nginx 部署建议：`TRUST_PROXY=1`，Nginx 设置 `X-Real-IP $remote_addr`。
- 命中失败返回 `403 ip_not_allowed`。

### 4.4 限流与配额

**Redis 维度：**

| 维度 | Key 设计 | 算法 |
|---|---|---|
| RPM | `rl:rpm:{keyId}:{epochMinute}` | 固定窗口计数 + 120s TTL |
| 并发 | `rl:conc:{keyId}` | INCR/DECR + 5min 兜底 TTL |
| 每日请求 | `rl:day:{keyId}:{yyyyMMdd}` | 固定窗口 + 2d TTL |
| TPM（P1） | `rl:tpm:{keyId}:{epochMinute}` | 预估预留 + 响应后校正 |

- 用 Lua 脚本一次完成“检查 + 扣减”，保证原子性。
- 并发槽位必须在 `finally` 释放；进程异常时靠 TTL 兜底。
- 固定窗口存在临界突刺，MVP 可接受；P1 可换滑动窗口计数。
- 超限返回 `429`，带 `retry-after` 和 `x-ratelimit-*`。
- Redis 不可用时策略可配置：
  - `fail-open`：放行，保可用性，但可能被刷。
  - `fail-closed`：拒绝，保安全，但 Redis 故障会影响业务。
  - 建议默认 `fail-closed` 用于 Key 级限流，管理端可配置。

**配额（DB 原子更新）：**

```sql
UPDATE api_keys
SET used_requests = used_requests + 1
WHERE id = $1
  AND (quota_requests IS NULL OR used_requests + 1 <= quota_requests)
RETURNING used_requests, quota_requests;
```

- 请求数在调用前扣；Token/成本在响应后按实际 usage 累加。
- 月度配额按自然月重置；每日请求按配置时区重置。
- 超限返回 `429 insufficient_quota`。

### 4.5 路由与故障转移

- 公共模型 → 多条路由，按 `priority` 升序。
- 同优先级按 `weight` 加权随机。
- 过滤：路由禁用、上游禁用、模型禁用、熔断中、能力不匹配。
- 重试预算：最多 2 次切换，受总超时约束；每次 attempt 记录上游、状态、耗时、错误。
- 熔断：60 秒内连续 5 次失败 → 打开 30 秒；半开放 1 个探测请求。
- 流式请求一旦向客户端写出首字节，不再重试，只发送错误收尾。
- 所有候选失败 → `503 no_available_upstream`。

### 4.6 敏感检测

**检测对象：**

- 输入：`messages[].content`（字符串或多模态文本片段）、`system`、工具调用参数。
- 输出：`choices[].message.content`、工具调用参数、reasoning 内容（若上游返回）。
- 跳过：图片 base64、二进制数据。

**检测流程：**

1. 提取文本片段，记录来源路径（如 `messages[2].content`）。
2. 归一化：NFKC、去零宽字符、大小写归一；保留“归一化索引 → 原文索引”映射。
3. 关键词：Aho-Corasick 多模式匹配，适合大词库。
4. 正则：RE2 或经过 safe-regex 校验 + 长度限制，避免 ReDoS。
5. 合并命中，按严重级别和规则动作决策：`block > mask > log`。
6. 单请求命中数上限（如 100），防止恶意构造导致 CPU 打满。
7. 返回命中详情：规则 ID、类别、方向、动作、脱敏片段、位置。

**流式检测：**

- 维护滑动窗口：`carry + delta`，保留 `max(256, maxKeywordLen - 1)` 字符作为重叠区。
- 每次只转发“安全前缀”，命中立即停止。
- 跨 chunk 的关键词必须能命中（单元测试覆盖）。
- 正则规则长度不可知，统一 holdback 256 字符；P1 支持按规则配置。

**日志脱敏：**

- 不记录完整命中值；只记录规则名、类别、位置、掩码片段（如 `138****8000`）。
- 请求/响应体捕获时，对 `Authorization`、`api_key`、`password`、`cookie`、`set-cookie` 以及命中片段做替换。

### 4.7 错误码

统一错误体：

```json
{
  "error": {
    "message": "Model is not allowed for this key",
    "type": "invalid_request_error",
    "param": null,
    "code": "model_not_allowed"
  },
  "request_id": "req_..."
}
```

| HTTP | code | 场景 |
|---|---|---|
| 400 | `invalid_request_error` | 参数错误、Body 过大、消息为空 |
| 400 | `content_policy_violation` | 输入敏感信息被拦截 |
| 401 | `invalid_api_key` | Key 不存在/格式错误 |
| 401 | `key_expired` | Key 过期 |
| 403 | `key_disabled` | Key 被禁用/吊销 |
| 403 | `ip_not_allowed` | IP 不在白名单 |
| 403 | `model_not_allowed` | 模型不在 Key 白名单 |
| 404 | `model_not_found` | 模型不存在/未启用 |
| 429 | `rate_limit_exceeded` | RPM/并发/每日请求超限 |
| 429 | `insufficient_quota` | 配额/Token/成本超限 |
| 502 | `upstream_error` | 上游返回错误 |
| 503 | `no_available_upstream` | 无可用路由/全部熔断 |
| 504 | `upstream_timeout` | 上游超时 |
| 500 | `internal_error` | 未预期异常 |

> 输出敏感拦截不使用 HTTP 错误码，使用 `finish_reason=content_filter`，并在响应头标记 `x-gateway-intercepted: output`。

### 7.2 Element Plus X 组件落地

| 组件 | 用途 |
|---|---|
| `Conversations` | 左侧会话列表；新建、重命名、删除、切换 |
| `BubbleList` | 消息气泡列表；user/assistant 角色、Markdown、代码块、复制、重新生成 |

**对话页布局：**

```
┌──────────────┬────────────────────────────────────────────┐
│ 会话列表      │  顶部：模型选择 / Key 选择 / 参数 / 清空       │
│              ├────────────────────────────────────────────┤
│ + 新建会话    │                                            │
│              │           BubbleList（消息区）              │
│ 会话 1        │                                            │
│ 会话 2        │                                            │
│              ├────────────────────────────────────────────┤
│              │  Sender（输入区）                           │
│              │  底部：Token / 延迟 / 拦截状态 / request_id   │
└──────────────┴────────────────────────────────────────────┘
```

**交互细节：**

- 模型下拉只展示当前 Key 有权限的模型。
- 参数抽屉：system prompt、temperature、top_p、max_tokens、stream 开关。
- 流式渲染：增量追加；自动滚动到底部，但用户上滚时暂停自动滚动。
- 停止生成：AbortController；后端释放上游连接和并发槽位。
- 重新生成：保留上下文，重新发起最后一条。
- 错误展示：区分网络错误、限流、模型无权限、输入拦截、输出拦截。
- 拦截提示：在消息流中插入一条系统提示，不展示命中的敏感原文。
- Markdown：DOMPurify 清洗，代码高亮，复制代码。
- 会话持久化：MVP 用 localStorage；P2 再做服务端会话。
- 图片输入：MVP 用 data URL，限制 5MB；P1 接对象存储。

### 7.3 管理端体验要求

- 表格：服务端分页、筛选条件同步到 URL、空状态、加载骨架。
- 表单：即时校验、错误定位、保存前二次确认（危险操作）。
- Key 创建成功：全屏/大弹窗展示一次，复制按钮 + “我已保存”勾选，关闭后不可再查看。
- 日志详情：时间线展示 `认证 → IP → 模型 → 限流 → 输入检测 → 路由 → 上游 → 输出检测 → 完成`。
- 敏感测试器：输入文本、选择方向、展示命中高亮、命中规则、最终动作、耗时。
- 危险操作（吊销 Key、删除上游、删除规则）二次确认并记录审计。
- 暗色主题、中文优先；文案避免暴露内部实现细节给普通调用方。

## 8. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 网关自身开销 P95 ≤ 50ms（不含上游）；流式首字节额外开销 ≤ 100ms；单实例 ≥ 100 并发流式连接（2C4G 基准，需压测验证） |
| 可用性 | 单实例可重启；多实例无状态；目标 99.9%（多实例 + 托管 DB/Redis） |
| 安全 | 密钥加密、Key 哈希、JWT、CORS、Helmet、Body 限制、SSRF 防护、登录限流、审计 |
| 隐私 | 默认不记录请求/响应正文；记录时脱敏；日志保留期可配；敏感命中不落原文 |
| 扩展性 | 适配器可插拔；新增上游协议只需实现 Adapter；路由/规则表驱动 |
| 兼容性 | OpenAI SDK（Python/Node）可用；SSE 标准；错误格式兼容 |
| 可观测 | 结构化日志、requestId、Prometheus 指标、健康检查 |
| 可维护 | 模块边界清晰；共享类型；迁移脚本；README 可一键启动 |
| 浏览器 | Chrome/Edge 最近两个大版本；1280px 以上；移动端只保证可查看 |

**SSRF 防护：**

- 上游 Base URL 只允许 `http/https`。
- 默认禁止私网、回环、链路本地、云元数据地址（`169.254.169.254` 等）。
- 如确需接 Ollama/内网网关，提供 `ALLOW_PRIVATE_UPSTREAMS=true` 或域名白名单。
- 禁止跟随重定向；DNS 解析后校验 IP，降低 DNS Rebinding 风险。
- 上游 TLS 证书默认校验；自签证书需显式配置 CA。

**日志与隐私：**

- 默认只记录元数据，不记录 messages 正文。
- 开启 Body 记录时：大小上限（如 64KB）、字段脱敏、单独表、单独保留期。
- `Authorization`、`Cookie`、`Set-Cookie`、密码、上游 Key 永不落日志。
- 客户端 IP 可配置“完整记录 / 掩码 / 哈希”。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 上游协议差异大（流格式、工具调用、错误码） | 适配器复杂、联调慢 | 定义内部统一事件模型；每家做 fixture 契约测试；先 OpenAI 后扩展 |
| 流式敏感检测漏检/误检 | 合规风险或误伤 | 滑动窗口 + 跨 chunk 单测；规则测试器；先 block/log，mask 后置 |
| 敏感词误报 | 正常业务被拦截 | 分级动作、log-only 观察期、白名单、按 Key 策略 |
| 限流临界突刺 | 短时超限 | 固定窗口 MVP；P1 滑动窗口；监控 429 比例 |
| Redis 故障 | 限流失效或全站拒绝 | 明确 fail-open/fail-closed；告警；Redis 高可用 |
| 日志量过大 | 存储成本、查询慢 | 默认不存 Body；保留期；索引；按月分区 |
| 密钥泄露 | 重大安全事件 | AES-GCM 加密、掩码、日志脱敏、最小权限、审计 |
| SSRF | 内网探测 | 私网黑名单、DNS 校验、禁重定向、白名单 |
| 范围蔓延（计费/多租户/RAG） | 延期 | 锁定 MVP 边界，P1/P2 另排期 |
| Element Plus X 版本波动 | 前端返工 | 锁定稳定版本；封装一层 Chat 组件，避免全站耦合 |
